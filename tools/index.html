The tools

A toolchain that treats specifications as data

TomSpecs is not a paper method. The specification is a typed object model, and the tools read, check and change it through that model - which fields exist, of what type, which Blueprint region a section expands, which code a section feeds - instead of editing text.

MODEL

The specification object model

Typed classes for all fourteen document roots, written in Dart with annotations for section ids, forms, content help, Blueprint mapping and code routing. A structural validator enforces the model's own rules before anything is generated from it.

  • tom_specs_core - the annotations
  • tom_specs_model - the model and its reference documentation
NINE LANGUAGES

Runtimes and typed facades

From the model, a generator writes a typed facade, a JSON metadata tree and DocSpecs schemas for Dart, Python, Java, JavaScript, TypeScript, Go, Rust, C and C++, each on a runtime with generic path access, YAML and Markdown serialization, validation and review annotations. One conformance corpus holds all nine to the same behaviour.

  • tom_som_dart_runtime, tom_som_dart_v0 on pub.dev
  • the other eight languages in source
DOCSPECS

Structured Markdown

Markdown documents that declare their schema in a header and give every heading a stable section id. A schema says which sections are required and what they hold; the validator checks a document against it. Every TomSpecs document has a DocSpecs rendition.

  • tom_doc_specs - schemas and validation
  • tom_doc_scanner - the Markdown parser
CLI

Validation and review tools

validate_spec checks any project's document on three tiers - it decodes against the model, meets its DocSpecs schema, and holds valid values and resolving references. extract_answers collects a review round's answers; generate_registry_tests writes the registry test suites of Phase 5; outliner renders the model's class tree.

  • tom_specs_clitool
CODESPECS

Specifications to code

The Cs* annotation family that marks a CodeSpec, the back-link annotation that cites its source sections, and the few classes Tom Core does not yet provide. The extract generator - in every runtime - routes each section to its code area; validate_codespecs runs the derivation contract's 41 checks over a generated project trio.

  • tom_code_specs, tom_core_codespecs
  • validate_codespecs in tom_specs_clitool
VS CODE

Tom AI extension

About sixty specification and CodeSpecs agent tools, running on the TypeScript runtime: outline, search, reflect and edit a specification in batches; annotate, answer and merge review rounds; run the CodeSpecs gate, extraction, verdicts and validation. A process view walks a quest through its phases, steps and gates, and a prompt queue hands each step to an agent.

  • source: al-the-bear/tom_vscode
  • not yet on the Marketplace

Every edit through the model

Whether a person types in the editor, an agent calls a tool, or a script uses a runtime, an edit is checked against the model: a path that does not exist is refused with the nearest one that does, a value of the wrong type is refused with the field's type and domain, and a batch of edits is written all at once or not at all. That is what makes it safe to let an agent write directly into a specification.

In development

The spec editor (tom_specs_editor) is a desktop application for working through the process: a model-driven document editor with structure browser, review and an embedded agent for Phases 2 and 3, and phase surfaces for CodeSpecs and implementation. A run surface for Phase 4, the implementation and acceptance views, deployment and operations follow in that order. It is not released yet.

Status

The Dart packages are published on pub.dev and their sources and documentation are public on GitHub; the other language runtimes, the VS Code extension and the editor are used from source for now. See Get started for the package list and the samples.
