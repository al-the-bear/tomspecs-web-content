The method

Eight phases, eight gates

TomSpecs defines how a system is built with the Tom architecture - from a free-form idea through specification, code specification, test derivation, implementation and acceptance to release - and how it continues once the system is in production.

The architecture is fixed: a Flutter client, a Dart server, a SQL database and the standard Tom components (Tom Core, user and access management, deployment, provisioning, subscriptions). Because every system is built from the same parts with the same layering, a specification can be mapped mechanically onto code, and the space in which an implementer can go wrong is small and well understood.

Principles

PrincipleWhat it means
TraceabilityEvery implementation element traces back to a business requirement, and every requirement forward to code and tests.
Model as truthThe specification object model is the source of truth; Markdown and YAML files are renderings of it.
Code as specA skeleton that compiles but does not execute is itself a specification artifact, the bridge between documents and implementation.
Test-firstTests are derived from the specification before implementation begins.
IncrementalEach piece is implemented and verified before the next one is started.
AI-driven, human-gatedAI agents produce and review the artifacts; people decide at the gates.
Iterative, not linearDeliverables loop until their quality holds, and a phase is re-entered when a later one exposes a defect in it.

Every gate can fail. A failed gate returns the work to its phase, and only the failed criteria are checked again. That rework loop is the normal case, not the exception: a gate that never fails has criteria that are too weak.

The Blueprint is the expansion point

Every Phase-3 document is derived from a defined region of the Solution Blueprint. The mapping is part of the object model - which Blueprint section maps to which document, which document elaborates a Blueprint subtree - and a validator enforces it. Phase 3 is therefore not "write twelve documents from scratch" but "expand each mapped region to specification depth", a bounded, checkable and largely AI-executable task. It is also why the Blueprint's gate is heavy: a defect that survives G2 is multiplied by twelve.

The phases

PHASE 1

Project Idea

Capture the vision completely, even where it is vague or contradictory - filtering is the Blueprint's job. Gather material in any form, write down every idea, sketch the boundaries, name who uses, owns and runs the system.

PHASE 2

Solution Blueprint

An AI fills the Blueprint from the idea; the model tells it what each section wants. Every section the idea cannot answer becomes an explicit question, not an invention. The business answers, a quality role reviews, the loop repeats until the document holds.

PHASE 3

Detailed Specifications

Each mapped Blueprint region is expanded in dependency order - RSP feeds TOM, ISC, SAS and QAP; IFM feeds ATS and persistence. Same concept, same term, same value everywhere; every requirement carries an id that everything downstream cites.

PHASE 4

CodeSpecs

The specification becomes a skeleton: screens, forms, fields and types, validations, layouts, endpoints, persistence classes, the database schema, errors, authorization. A gate at the start checks that the specification is good enough to derive code from. More below.

PHASE 5

Test Derivation

Acceptance tests from the scenarios and the quality plan, boundary tests from the requirements, authorization tests from SAS, data tests from IFM, integration tests from IIS. Registry suites are generated. Every test maps to its CodeSpec and requirement; all start red.

PHASE 6

Implementation

In dependency order: schema, data models, server endpoints, UI data models, UI actions, UI elements. For each element: confirm red, implement the minimum, green, refactor, add unit tests, commit. The framework owns security, transport and persistence - only business code is written.

PHASE 7

Application Candidate

Deployed to a test environment and run through the business's own quality plan: user flows end to end, the real external integrations, the non-functional targets. User documentation is derived and walked against the candidate. Defects go back to Phase 6.

PHASE 8

Release Candidate

Production configuration, a rehearsed rollback, monitoring, security hardening, verified data migration, a controlled rollout. Optionally multi-tenant: per-client provisioning, subscription plans, quotas and feature toggles.

Phase 4 in detail: two passes with a fixed boundary

A CodeSpec is an ordinary Dart class built on an existing Tom Core class and marked with Cs* annotations. Phase 4 is neither a compiler pass nor free authoring; it runs in two passes:

PassDone byProduces
1 · ExtractThe extract generatorOne bounded extract per code area, holding every specification field routed to that area, verbatim and with its source. It may copy and index; it may not summarise, rephrase or choose a name.
2 · AuthorThe authoring agentThe CodeSpecs Dart, one step at a time in a fixed order, each step reading only its own extracts and following the derivation contract.

The split exists because the two halves fail differently: a mechanical rule applied to prose invents structure that is not there, and an author handed the whole specification reads the wrong parts of it.

The starting gate. Before any code is written, the specification must be complete against its schema, valid, fully routed, and - per code area - sufficient: each area's extract alone has to be enough to author it. A specification with holes does not produce code with holes; it produces code with inventions. Where an input is missing, the result is a decision needed that pauses the run until it is answered in the specification.

The output is three projects split by where the code runs: _codespec_shared (API contracts, error results, shared enums and validations), _codespec_client (forms, layouts, actions, screens, navigation) and _codespec_server (services, database, handlers, authorization, migrations, jobs). Every declaration carries a back-link to the specification sections it came from, so Phases 5 and 6 read code rather than reopening the documents.

The quality gates

An orchestrator agent evaluates every criterion, collects the evidence and writes a gate report; people make the decision. Re-evaluation checks only the failed criteria; three failures in a row on one criterion escalate to a person. Every gate also reviews the risk register.

Quality inside a phase

The gates sit between phases; most of the quality work happens inside them, on three levels: a phase can be re-entered, each deliverable loops until it holds, and producing a derived deliverable routinely exposes a gap in its basis that has to be fixed upstream first.

The per-deliverable loop

Every deliverable - a Blueprint section, a document, a CodeSpecs part, a test group - moves between its progress role and its quality role: in progress, quality review, rework, and a human review before it is approved. The quality review asks four questions: is it correct (the business intent), consistent (with itself and its neighbours), comprehensive (edge cases, error paths, no unstated assumptions) and well-structured (schema, ids, navigable)?

The document sequence

In Phases 2 and 3 each document passes Draft (schema-valid, required sections present) → Reviewed (complete, faithful to its Blueprint region, no ambiguity) → Verified (references resolve, consistent with related documents) → Accepted. A failure at any stage returns it to Draft with a findings report, and the phase gate cannot pass until every required document is accepted.

A step plan for Phases 2 and 3

The work runs in fixed steps, each with its own folder: an initial version derived from the source, a deepening along each document's structure, repeated rounds of questions, a structural and requirements pass and a consistency round until no relevant question is left open, a final consistency iteration, and the result - a document with no open question or comment left in it.

Review rounds happen inside the documents

Human review and the agent's clarifications live in the specification itself, as comments, questions with lettered options and inline change marks. A side file may index the questions; it never holds them - the position in the text is the context. A round runs in four steps: annotate, apply one item at a time, record each applied item in the decision log, and only then remove it. Annotations are never stripped in bulk: an item removed before it is applied and logged is lost without trace.

Sessions expire after 30 minutes of inactivity.
> ⬆️ **C-12** (Alexis): Too long for shared kiosk devices.
> **❓ BQ-90 — C-12 kiosk timeout:** a shorter timeout for kiosk devices only,
> or for every device?
> - **(a)** kiosk devices only, 5 minutes
> - (b) every device, 15 minutes
>
> *Recommendation:* (a). *Working assumption until answered:* (a).
>
> **Answer:** (a)

Inline marks use CriticMarkup - {~~ 30 ~> 5 ~~}, {++ added ++}, {-- removed --} - and are accepted or rejected one by one. Team rounds hand each reviewer a copy and merge the copies back, with conflicting changes shown side by side for a decision.

Roles

In every phase a progress role drives the deliverable forward and a quality role reviews, challenges and iterates with it - a dialogue partner during the work, not a gatekeeper at the end. The two must run as separate agents: one agent checking its own work is not independent verification.

After release: upgrade cycles

Once a system passes G8 it leaves the creation process. Changes - features, technology updates, compliance, security, capacity, new external systems - run through an upgrade cycle: change collection, impact analysis, specification update, CodeSpecs update, test update, implementation, release. The previous release is the baseline and regression is the primary concern: only the affected documents change, gates evaluate the delta plus the full regression suite, database changes are migrations, and the traceability chain is what makes the impact set computable.

The full process definition, with every gate checklist, the role catalogue, the issue workflow and the upgrade cycle, is the TomSpecs project flow.
